# CHG-007 / F1-07 — Tres tareas ejecutables

> **Dependencia BLOQUEANTE:** antes de Apply confirmar CHG-006/F1-06 implementado, integrado y con pruebas **locales Docker aisladas** de instalación y actualización aprobadas. El gate del VPS público sigue separado antes de producción. No confundir planificación CHG-006 con infraestructura funcional. No iniciar CHG-008, merges o archive automáticamente. Máximo 3 tareas.

- [x] **1. OPS — Healthchecks, logs rotados y alertas ligeras.** Configurar healthchecks para Next.js, PostgreSQL y Caddy; logs estructurados con rotación y límites; alertas esenciales de caída/backup mediante notificación externa sencilla. En desarrollo puede usarse un receptor aislado sintético para probar el flujo, sin considerarlo sustituto de una notificación externa real antes de producción. Sin Prometheus/Grafana/ELK u otros servicios sin justificación. **Evidencia:** rutas live/ready y healthchecks de los tres servicios; driver JSON con rotación 3×10 MiB y Caddy JSON validado; receptor loopback recibió 12 transiciones (6 alertas/6 cierres) para servicios, WAL y marcador de backup; 1,958 líneas de logs de los contenedores CHG-007 no contenían credenciales sintéticas; 30 pruebas unitarias incluyen cobertura de la bandera externa genérica para fallo de backup y del issue inmediato `backup:failed`. La entrega de alertas externas permanece como gate de producción.

- [x] **2. DB/OPS — pgBackRest y almacenamiento S3 de prueba aislado.** Mantener pgBackRest; ejecutar SeaweedFS `weed mini` en un proyecto Docker independiente y desechable, sin exposición pública, con imagen fijada por versión o digest, datos y credenciales sintéticos. Demostrar compatibilidad S3 real para backup cifrado, restore, archivado y recuperación WAL con las versiones fijadas. Si falla una operación requerida, evaluar y justificar una alternativa S3 compatible mantenida antes de implementarla. Producción requiere repositorio cifrado fuera del VPS, credenciales independientes y recuperación comprobada. **Evidencia:** pgBackRest 2.60.0 y SeaweedFS 4.51 fijados; `stanza-create`, `check`, full backup AES-256-CBC, `info`, archive WAL, restore y PITR reales completados; al detener S3 el backup falló con código 1 sin actualizar su marcador, y tras recuperarlo volvió a pasar. Configuración aislada sin puertos publicados, secretos sintéticos externos y verificación de TLS estricta obligatoria en configuración de producción. La prueba local no acredita almacenamiento externo real.

- [x] **3. QA — Restauración desechable y RPO/RTO observados.** Restaurar backup/PITR con datos sintéticos en una instalación PostgreSQL desechable; comprobar integridad y servicio. Registrar timestamps UTC, RPO observado (objetivo <=15m), RTO observado (objetivo <=4h), transacciones confirmadas/recuperadas, pérdidas posibles y límites de la simulación. Si se incumple o falta evidencia, no aceptar la tarea. Documentar el runbook; no extrapolar a producción ni tocar stacks existentes. **Evidencia:** pérdida simulada del contenedor/volumen fuente etiquetados y restore en volumen nuevo; PITR a `2026-11-02T20:14:28.003199Z` recuperó `before-target`, excluyó `after-target`; ledger Drizzle 1 fila y app healthy a `20:16:01.384553Z`. RPO observado 3.760436 s y RTO 68.914522 s. Runbook registra timestamps, posible pérdida y límites locales. Esto no valida una instalación o garantía de producción.
