# CHG-006 / F1-06 — Tres tareas ejecutables

> **Precondición:** CHG-003 y CHG-005 integrados en `main`; antes de Apply leer `compose.yaml`, `next.config.ts`, `scripts/db-migrate.ts`, reglas de URLs locales y `docs/operations/pr-quality-policy.md`. Planificación independiente; no iniciar CHG-007, no hacer merge/archive automáticamente. Máximo 3 tareas principales.

- [x] **1. OPS — Docker Compose para app y PostgreSQL por instalación.** Implementar imagen Next.js reproducible y Compose de despliegue separado del Compose local, con app no-root, PostgreSQL 18.6 compatible, volúmenes/redes/credenciales aisladas por restaurante, healthchecks y configuración autorizada externa. Preservar `dosvy-chg003` y recursos de CHG-004; no exponer DB/app directamente. **Evidencia:** build limpio, `docker compose config`, validación de secretos obligatorios y prueba de dos proyectos independientes sin solapamiento.

- [x] **2. OPS — Caddy y aislamiento de red.** Mantener Caddy como único punto público previsto 80/443, `reverse_proxy`, TLS y certificados persistentes; verificar Caddyfile, HTTP→HTTPS **local**, redes privadas y ausencia de puertos publicados para DB/app; documentar DNS/firewall/SSH y verificación externa obligatoria antes de producción. **Evidencia:** Caddyfile validó en ambos proyectos; HTTP respondió 308 hacia HTTPS y HTTPS local 200 para `localhost`, con certificado emitido por `Caddy Local Authority - ECC Intermediate`, identificado como certificado de prueba y no TLS público. El mismo fingerprint persistió tras reiniciar Caddy y recrear ambos stacks. Inspección Compose/runtime confirmó red de datos interna, PostgreSQL solo en data, Caddy solo en edge, app en ambas redes, sin puertos publicados de DB/app y puertos Caddy ligados a loopback. Secretos sintéticos externos con ACL restringida; el checker aceptó rutas externas y rechazó una ruta dentro del repo sin imprimir valores.

- [x] **3. QA — Instalación limpia y actualización reproducible.** Verificar bootstrap, migraciones con guardias independientes, instalación limpia y actualización **en proyectos Docker aislados con datos sintéticos**, health/smoke, dos instalaciones independientes, idempotencia y limpieza sin tocar otros recursos; documentar rollback de imagen sujeto a compatibilidad del esquema. Correr QA y OpenSpec strict. **Evidencia:** dos proyectos exclusivos con DB, credenciales, redes y tres volúmenes separados; instalación limpia y migraciones completadas en ambos. Repetir migraciones mantuvo una fila por ledger. A se actualizó de `dosvy-chg006:local-e84487d` a la imagen construida desde HEAD `4a15f46` y pasó health/smoke; B arrancó directamente con la imagen nueva. `compose down` sin `-v` conservó los volúmenes; recrear stacks mantuvo ledger, certificados y salud. Ambos proyectos se limpiaron por nombre exacto; no quedaron recursos temporales y el contenedor/volumen/red de CHG-003 conservaron ID/estado/nombre. El runbook documenta rollback de imagen solo con esquema compatible y nunca rollback SQL automático. Typecheck, lint, boundaries, build, 12 unit, 12 integration, 3 E2E, `db:check`, TruffleHog, auditoría y OpenSpec strict pasaron. El gate público sigue pendiente por separado.

> Evidencia de implementación (2026-11-01): T1 completada con build Docker standalone, configuración sintética válida y rechazo por variables ausentes, guardias de rutas/credenciales/digests, dos proyectos con redes/volúmenes/bases distintas y app/PostgreSQL/Caddy saludables. Las migraciones de despliegue se aplicaron a ambas bases; repetir en la instalación A dejó una sola fila en el ledger. Inspección confirmó que solo Caddy publicó puertos, ligados a loopback durante la prueba, y que `dosvy-chg003-postgres`/`dosvy_chg003_pgdata` permanecieron intactos.
